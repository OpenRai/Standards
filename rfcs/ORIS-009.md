# The `payto:` URI Scheme for Nano

> Status: Working Draft
> Category: Application Interface

## Abstract

This document defines the `nano` payment target type for the `payto:` Uniform Resource Identifier scheme (RFC 8905), and specifies MUST-level generation and parsing rules for Nano applications that produce or consume `payto:nano` URIs. RFC 8905 defines the generic envelope but explicitly delegates authority-specific path structure, options, and amount semantics to each payment network. Nano currently has no normative definition of its own; this document supplies one, so that any application implementing it can interoperate as a `payto:` URI producer or consumer regardless of platform or wallet.

## Motivation

`payto:` support has shipped in multiple independently developed Nano wallets for several years, informally documented on nano.community, but never specified at the level required for guaranteed cross-wallet interoperability. Comparing RFC 8905's own grammar against the existing community documentation surfaces at least three concrete ambiguities:

- **Authority delimiter**: RFC 8905 requires `payto://` (double slash) before the authority. Existing community examples show `payto:nano/...` (single slash).
- **Option name character set**: RFC 8905's `opt-name` grammar only permits `ALPHA`, `DIGIT`, `-`, and `.`. Some existing documentation and/or implementations use underscore-separated names (`receiver_name`) alongside the RFC-conformant hyphenated form (`receiver-name`).
- **Amount precision**: Nano's raw unit is 10^30 per whole XNO, well outside IEEE-754 double precision. Undefined behavior here is a real fund-loss risk, not just a cosmetic inconsistency.

None of these are hypothetical concerns — they are exactly the class of divergence that causes a URI generated by one wallet to fail, or silently misresolve, in another. This document exists independently of, and prior to, any corresponding docs.nano.org integration-guide update, and is intended to become the normative reference such an update would eventually cite rather than duplicate.

## Conventions

The key words MUST, MUST NOT, SHOULD, SHOULD NOT, and MAY in this document indicate normative requirements.

Unless otherwise stated:

- `payto:` refers to the URI scheme defined by RFC 8905.
- `nano:` refers to the pre-existing native Nano URI scheme documented at [docs.nano.org's URI and QR Code Standards](https://docs.nano.org/integration-guides/the-basics/#uri-and-qr-code-standards) section. This document does not redefine `nano:` — see [Relationship to the `nano:` Scheme](#relationship-to-the-nano-uri-scheme).
- CAIP-2, CAIP-10, `nano:mainnet`, and the canonical `nano%5F`-prefixed account ID form refer to the definitions in [ORIS-006](./ORIS-006.md). This document does not redefine them — see [Relationship to ORIS-006 CAIP Identifiers](#relationship-to-oris-006-caip-identifiers).
- "producer" refers to any application generating a `payto:` URI or corresponding QR code for display, sharing, or transmission.
- "consumer" refers to any application registering as a URI/QR handler for, or otherwise parsing, such a URI.
- 1 XNO = 10^30 raw, consistent with the [ORIS-007 glossary](./ORIS-007.md#glossary).

## Specification

### Scope

This document covers:

- the `nano` payment target type for `payto:` (`payto://nano/...`)
- normative generation rules for producers
- normative parsing rules for consumers
- the minimum behavior required for an application to register itself as a `payto:` URI/QR handler on a given platform (informative)
- a compatibility matrix tracking current wallet behavior against this specification, pending community input

This document does not cover:

- redefining the existing `nano:` scheme's own syntax — only its relationship to `payto:`
- non-Nano `payto:` payment target types already defined by RFC 8905 itself (`ach`, `bic`, `iban`, `upi`, `bitcoin`, `ilp`, `void`)
- payment correlation or metadata conventions — see [ORIS-007](./ORIS-007.md)
- NanoNym stealth-address payment targets — reserved as future work; see [Open Questions](#open-questions)

### Relationship to the `nano:` URI Scheme

`nano:` predates widespread `payto:` adoption in the Nano ecosystem and remains the primary scheme documented at docs.nano.org. `payto:` is the IANA/IETF-registered, cross-payment-network equivalent. Applications SHOULD support both. Neither scheme is authoritative over the other with respect to the payment it describes — a payment request MAY be represented as either or both, and the resolved address, amount, and recipient metadata MUST be identical between the two representations for a given request. When a producer displays a single QR code or deep link to an audience that may include non-Nano-specific tooling (e.g. generic payto-aware handlers), it SHOULD prefer `payto:`.

### Relationship to ORIS-006 CAIP Identifiers

ORIS-006 defines the canonical CAIP-10 account ID for a Nano account as `nano:mainnet:nano%5F<account-body>`, with the underscore percent-encoded. That encoding is required there because the CAIP-10 `account_address` grammar restricts characters to `[-.%a-zA-Z0-9]{1,128}`, which excludes a raw `_`.

The `payto:` `path-abempty` component is governed by a different grammar — RFC 3986 `pchar`, via its `unreserved` production — which explicitly includes `_` alongside `ALPHA`, `DIGIT`, `-`, `.`, and `~`. Consequently:

- Producers MUST use the native, unencoded form (`nano_<account-body>`) in the `payto:` path. Percent-encoding the underscore in a `payto:` URI is unnecessary, non-canonical, and MUST NOT be done — carrying ORIS-006's CAIP-10 encoding habit into `payto:` produces a technically-valid-but-nonstandard URI that a strict consumer may fail to match against the canonical form below.
- The two identifier forms are equivalent representations of the same account and MUST decode to an identical canonical Nano address string after their respective normalization rules are applied:

  | Form | Canonical string |
  |---|---|
  | `payto:` URI | `payto://nano/nano_<account-body>` |
  | ORIS-006 CAIP-10 | `nano:mainnet:nano%5F<account-body>` |
  | Underlying Nano address | `nano_<account-body>` |

- Implementations that support both a `payto:` handler surface and a CAIP-10/session-protocol surface (e.g. WalletConnect-style flows referencing ORIS-006) MUST treat a `payto:` URI's address and a CAIP-10 account ID as the same account whenever their decoded, canonicalized `nano_<account-body>` values match. This document does not define a `payto:` option for carrying a full CAIP-10 string or a CAIP-2 chain reference — the `nano` authority alone is treated as implicitly equivalent to `nano:mainnet`, consistent with ORIS-006 defining only mainnet for public interoperability. A future ORIS document MAY define an authority-specific option for non-mainnet Nano networks if that ever becomes necessary; producers and consumers MUST NOT invent one unilaterally in the meantime.

### ABNF Syntax

The generic grammar below is RFC 8905 §2, reproduced for reference; the `nano`-specific additions are new in this document.

```abnf
; Generic payto grammar (RFC 8905 §2)
payto-URI      = "payto://" authority path-abempty [ "?" opts ]
opts           = opt *( "&" opt )
opt            = opt-name "=" opt-value
opt-name       = generic-opt / authority-specific-opt
opt-value      = *pchar
generic-opt    = "amount" / "receiver-name" / "sender-name" / "message" / "instruction"
authority-specific-opt = ALPHA *( ALPHA / DIGIT / "-" / "." )

; Nano-specific additions (this document)
authority      =/ "nano"
path-abempty   = "/" nano-address
nano-address   = ("nano_" / "xrb_") 60( base32-nano-char )
```

Producers MUST emit URIs of the form `payto://nano/<nano-address>[?<opts>]`, using the double-slash authority delimiter required by RFC 8905 §2.

> **[OPEN QUESTION — pending compatibility matrix]** Existing community reference text shows a single-slash form (`payto:nano/nano_...`), which does not conform to the RFC 8905 ABNF. If any shipping wallet only parses or generates this form, that wallet is non-conformant to both RFC 8905 and this document. Pending confirmation, consumers SHOULD accept the single-slash form for backward compatibility, but producers MUST NOT generate it.

### Address Encoding

- `nano-address` MUST be a full, checksum-valid encoded Nano account string, given natively — i.e. `nano_`/`xrb_` and the underscore therein MUST NOT be percent-encoded. RFC 3986's `pchar`/`unreserved` production permits `_` in `path-abempty` directly; percent-encoding it is unnecessary and non-canonical here. (This differs from [ORIS-006](./ORIS-006.md)'s CAIP-10 account ID, whose stricter `account_address` grammar requires percent-encoding the underscore as `%5F` — see [Relationship to ORIS-006 CAIP Identifiers](#relationship-to-oris-006-caip-identifiers).)
- Producers MUST use the `nano_` prefix.
- Consumers MUST accept both `nano_`- and `xrb_`-prefixed addresses, and MUST validate the embedded Blake2b-40 checksum before treating the URI as actionable. A URI whose address fails checksum validation MUST be rejected outright, not truncated or best-effort recovered.

### Query Parameters

| Name | Source | Requirement | Notes |
|---|---|---|---|
| `amount` | generic-opt | MAY be present | See [Amount Representation](#amount-representation) |
| `receiver-name` | generic-opt | MAY be present | Canonical hyphenated form |
| `sender-name` | generic-opt | MAY be present | Defined by RFC 8905; not yet exercised by existing Nano wallet docs |
| `message` | generic-opt | MAY be present | Free-text, producer-supplied, unauthenticated |
| `instruction` | generic-opt | MAY be present | Defined by RFC 8905; no Nano-specific semantics assigned yet |

Producers MUST NOT emit underscore-separated option names (e.g. `receiver_name`) — the RFC 8905 `opt-name` grammar only permits `ALPHA`, `DIGIT`, `-`, and `.`; underscores are not legal. Consumers MAY accept underscore variants for backward compatibility with non-conformant producers, but MUST treat the hyphenated form as canonical when generating.

No `nano`-specific `authority-specific-opt` values are defined by this document. Consumers MUST ignore unrecognized authority-specific options that do not affect address resolution or amount, to preserve forward compatibility with future extensions (e.g. NanoNym targets, correlation identifiers per ORIS-007).

### Amount Representation

- Format per RFC 8905: `amount=[<currency>:]<value>`.
- When no currency prefix is given, `<value>` MUST be interpreted as raw units, and MUST be an unsigned base-10 integer string — no decimal point, no scientific notation, no separators. Producers MUST NOT emit floating-point-formatted raw amounts.
- When a currency prefix is given (an ISO 4217 code, or the literal token `XNO`), consumers MUST convert to raw using 1 XNO = 10^30 raw, performed with arbitrary-precision/bigint arithmetic. Consumers MUST NOT perform this conversion using native IEEE-754 double-precision floats — that representation cannot hold 10^30 exactly, and this exact class of bug has caused fund-loss incidents in other ecosystems.
- Fiat-denominated amounts require an exchange-rate lookup that is inherently non-atomic between URI generation and consumption. Producers SHOULD prefer emitting raw or `XNO`-denominated amounts directly, and MAY omit `amount` entirely for open-ended requests (tips, donations).

### Generation Rules (Producer Requirements)

Producers:

- MUST emit `payto://nano/<nano-address>`, `nano_`-prefixed, double-slash form.
- MUST percent-encode option values per RFC 3986 `pchar` rules (in particular, spaces in `receiver-name` and `message`).
- MUST NOT emit float-formatted raw amounts.
- SHOULD also emit a companion `nano:` URI when the display context is Nano-specific (see [Relationship to the `nano:` Scheme](#relationship-to-the-nano-uri-scheme)).
- SHOULD include `receiver-name` where a stable, meaningful recipient identity exists.

### Parsing Rules (Consumer Requirements)

Consumers:

- MUST accept options in any order.
- MUST validate the address checksum before treating a URI as actionable.
- MUST reject the URI outright if the `amount` value or address fails validation; MUST NOT silently coerce, truncate, or round.
- MUST ignore unrecognized authority-specific options that don't affect address or amount resolution.
- MUST NOT prefill and auto-submit a transaction without explicit user review — the confirmation UI MUST display the full, untruncated destination address and the resolved amount (in both raw and a human-readable unit) before any signing occurs. This extends RFC 8905 §8's general prohibition on unreviewed transaction initiation with a Nano-specific requirement: because Nano sends are irrevocable and confirm in under a second, an ellipsized or truncated address in the confirmation dialog is a distinct phishing vector from the ones RFC 8905 already addresses.
- MUST NOT present `receiver-name` or `message` in a way that could be mistaken for consumer-verified identity (e.g., a verified badge) — these fields are producer-supplied and unauthenticated.

### URI Handler Registration (Informative)

This section is non-normative; verify exact mechanisms against current platform documentation before implementing.

- **Android**: register an `intent-filter` with `android:scheme="payto"` (and separately `"nano"`).
- **iOS / macOS**: register `"payto"` and `"nano"` under `CFBundleURLSchemes`.
- **Web**: `navigator.registerProtocolHandler()` has partial and inconsistent browser support for custom schemes; treat as supplementary, not primary. This is a distinct integration surface from the W3C Payment Request / Payment Handler API path and is out of scope here.

## Open Questions

- Single-slash vs. double-slash authority delimiter — resolve empirically via the compatibility matrix before this leaves Draft.
- Whether `sender-name` and `instruction` (defined by RFC 8905, unused so far in Nano wallets) should be given Nano-specific semantics in v1 or explicitly deferred.
- Whether a future NanoNym-based `payto:` target type (building on ORIS-002/ORIS-005) belongs in this document or a successor.

## Published Test Vectors

This document reuses [ORIS-006](./ORIS-006.md)'s published account body for continuity across the series:

```text
3noms9a1zytox399kygpge6cc7hu1z79ms1cgzojodz8741qi7w5u3nzb8mn
```

### Vector 1 — Canonical `payto:` Form

Input (native Nano address):

```text
nano_3noms9a1zytox399kygpge6cc7hu1z79ms1cgzojodz8741qi7w5u3nzb8mn
```

Canonical `payto:` output:

```text
payto://nano/nano_3noms9a1zytox399kygpge6cc7hu1z79ms1cgzojodz8741qi7w5u3nzb8mn
```

### Vector 2 — Equivalence with ORIS-006 CAIP-10 Form

The following two identifiers MUST be treated as denoting the same account:

```text
payto://nano/nano_3noms9a1zytox399kygpge6cc7hu1z79ms1cgzojodz8741qi7w5u3nzb8mn
nano:mainnet:nano%5F3noms9a1zytox399kygpge6cc7hu1z79ms1cgzojodz8741qi7w5u3nzb8mn
```

Note the underscore is raw in the `payto:` form and percent-encoded (`%5F`) in the CAIP-10 form — both decode to the identical canonical address `nano_3noms9a1zytox399kygpge6cc7hu1z79ms1cgzojodz8741qi7w5u3nzb8mn`.

Further vectors — in particular for the [open questions](#open-questions) around slash count and option-name casing — should be added once the compatibility matrix confirms the canonical forms in production use.
